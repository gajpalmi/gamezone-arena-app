PART 2 — PUBLIC BUSINESS / PRODUCT / SERVICE CONTACT DESIGN

Design a secure database-level solution where public users can contact an approved Business/Product/Service listing ONLY when:

- Listing is approved/public.
- Owner has explicitly enabled contact sharing.
- Contact value exists.
- The contact value belongs to that listing owner.
- User is not blocked where blocking is applicable.
- Only the minimum required contact field is returned.

The public client must NOT be able to directly SELECT private contact columns from the raw tables.

Design:

A) Safe RPC/projection for public contact.

Example concept:

get_public_business_contact(business_id)

and/or

get_public_offering_contact(offering_id)

But choose the correct names and structure after inspecting the existing schema.

The RPC must return only:

- listing ID
- contact type
- contact value
- optional display name if genuinely required

NEVER return:

- private owner profile data
- consent internals unnecessarily
- auth IDs
- unrelated phone/email
- private application information
- admin information

Explain whether SECURITY DEFINER or SECURITY INVOKER is safer here and why.

If SECURITY DEFINER is required, design:

- fixed search_path
- strict auth checks
- explicit grants
- EXECUTE only for intended roles
- no PUBLIC execution
- no dynamic SQL unless absolutely necessary
- no privilege escalation

PART 3 — EMPLOYER → WORKER CONTACT SECURITY

The existing worker contact RPC is profile-ID based.

Design a replacement that is relationship-bound.

The employer should receive worker contact information ONLY when ALL required conditions pass:

1. Employer is authenticated.
2. Employer owns the relevant job.
3. Worker is the applicant for that job.
4. The application belongs to that exact job.
5. Application status permits employer-worker contact.
6. Worker has explicitly allowed contact according to the existing consent model.
7. Neither side is blocked where applicable.
8. Contact information exists.
9. The requested contact belongs to that worker.
10. The caller cannot substitute another worker/profile ID to obtain contact data.

Design a safe RPC such as:

get_authorized_worker_contact(application_id)

Use the actual existing schema/naming after inspection.

The RPC must verify the complete chain:

authenticated user
→ employer
→ owned job
→ application
→ correct worker
→ valid application status
→ consent
→ block rules
→ contact availability

It must NOT trust a raw profile_id supplied by the client.

Explain exactly how User A attempting to access User B's worker contact is rejected.
